# Jev로 줄어든 것과 줄지 않은 것

2026-09-22에 새 `jev-workflow`의 효과를 측정했다. 결과부터 말하면, 이 실험에서 **Astra 입력은 1.4%, Astra 출력은 41.1% 줄었다. 그러나 Jev까지 포함한 토큰 수를 단순 합산하면 3.9% 늘었다.** 서로 다른 공급자의 토큰 수이므로 이것을 비용이나 Codex 한도 소모의 증감으로 해석할 수는 없다.

작은 입력 절감도 결과다. 원하는 숫자가 나올 때까지 다시 실행하거나, 미판단을 정답으로 처리하지 않았다. 아래에는 코드만 사용했을 때의 미판단도 함께 남겼다.

## 무엇을 비교했나

같은 6개 합성 사례를 조건마다 두 번씩 처리했다. 알려진 파일 조회, 단일 설정 수정, 오류 조사, 8건의 고정 분류, 독립적인 체크리스트 작업, 순차적인 혼합 작업이다. 파일을 실제로 수정하는 대신 각 작업을 어느 경로로 처리할지 고르는 실험이다.

- **A — Astra 직접 판단:** 짧은 원본 작업 메타데이터를 읽고 경로를 고른다.
- **B — 코드만 사용:** 명확한 4건은 코드가 결정하고 혼합 작업 2건은 UNKNOWN으로 남긴다. Astra는 짧은 결과를 JSON으로 반환한다.
- **C — 코드+Jev:** 명확한 4건은 코드가, 혼합 작업 2건은 Jev가 결정한다. Astra는 B와 같은 형식의 짧은 결과를 JSON으로 반환한다.

따라서 C는 Astra에게 이미 판단한 결과를 건네는 조건이다. 같은 정보를 읽고 추론 능력이 좋아졌다는 실험이 아니다. 원문을 사전 처리한 결과로 대체했을 때 다음 모델 호출에 들어가는 양과 결과를 비교했다. 구조화된 경로만 필요한 실제 코드에서는 이 마지막 Astra 출력 단계도 생략할 수 있지만, 그 효과를 이번 절감률에 섞지 않았다.

실행 순서는 **A1 → B1 → C1 → C2 → B2 → A2**로 미리 정했다. 같은 CLI에 `gpt-6-astra`, `ultra`를 지정하고 공통 프롬프트·읽기 전용 샌드박스를 사용했다. 변하는 사용자 설정과 프로젝트 문서는 모든 조건에서 제외했다. 실제 데스크톱의 전체 설정을 재현한 실험은 아니다. 모델별 응답에서 내부 서빙 버전은 별도로 제공되지 않았다. Jev 응답 모델은 `jev-1.13.0`이었다.

## 조건별 평균

각 행은 **6개 사례를 한 번 처리하는 데 든 평균**이다. 출력 토큰에는 보고된 추론 토큰이 포함되므로 다시 더하지 않았다.

| 조건 | Astra 입력 | Astra 출력 | 그중 추론 출력 | Jev 입력 / 출력 | 결과, 매 반복 |
| --- | ---: | ---: | ---: | ---: | --- |
| A: Astra 직접 | 18,975 | 92.5 | 45.5 | 0 / 0 | 정답 6, UNKNOWN 0 |
| B: 코드만 | 18,698 | 66.5 | 26.5 | 0 / 0 | 정답 4, UNKNOWN 2 |
| C: 코드+Jev | 18,705 | 54.5 | 8.5 | 938 / 109 | 정답 6, UNKNOWN 0 |

A와 C는 같은 6개 사례를 두 번 평가해 각각 12/12 정답이었다. B는 8/12 정답이고 나머지 4건은 UNKNOWN이었다. **독립적인 12개 실무 과제에서 정확도가 같았다는 뜻은 아니다.** UNKNOWN을 잘못된 확정 답으로 바꾸지 않은 것은 안전한 처리지만, 정답 수에 포함하지 않았다.

전달한 프롬프트는 A 2,686바이트에서 C 1,495바이트로 **44.3% 줄었지만**, 전체 Astra 입력은 **270토큰, 1.4%만 감소**했다. B도 입력이 277토큰 줄었다. 이 사례에서 입력 감소의 대부분은 코드가 원문 메타데이터를 짧은 결과로 바꾸면서 생겼다. Jev의 추가 역할은 코드만으로 남긴 혼합 작업의 UNKNOWN 두 건을 판단한 것이다.

C의 출력 41.1% 감소는 Astra에 한정된다. Jev 출력까지 더하면 평균 163.5토큰으로 A의 92.5보다 많다. 전체 입력·출력을 공급자 구분 없이 더하면 A는 **19,067.5**, C는 **19,806.5**다. 이는 토큰 개수의 장부상 비교이며 가격·할당량 비교가 아니다. Jev가 무료여도 호출과 데이터 처리가 사라지는 것은 아니다.

| B2 | 18,698 | 0 | 58 | 18 | 4 / 2 | 7.115초 | 0.217ms |

모든 실행이 종료 코드 0으로 끝났고, 시간 초과·형식 오류·도구 호출·누락·재실행은 없었다. C는 반복마다 Jev를 2번 호출했다. 저장 계획을 다시 읽는 별도 확인에서는 추가 Jev 호출이 0회였다. 계획 재사용과 Astra 입력 캐시는 다른 측정이다.

Astra 시간에 전처리 시간을 더하면 A 평균 7.679초, C 약 7.491초다. 차이는 약 0.19초에 불과하며 반복도 두 번뿐이다. 이를 속도 개선의 증거로 쓰지 않는다. 전처리와 Astra는 따로 측정했고 전처리는 모델 실행에 앞서 완료했으므로, 이 합계 역시 실제 사용자 작업 전체의 벽시계 측정은 아니다.

## 무엇을 주장할 수 없나

이 결과는 전체 코딩, 브라우징, iOS 조작의 절감률이나 성공률을 측정하지 않았다. 실제 앱 수정과 필수 테스트의 수행 능력도 비교하지 않았다. 사례는 작성한 정책에 맞춘 작고 단순한 합성 데이터이며 무작위 실무 표본이 아니다. 평균을 일반화하거나 정확도 동등성·통계적 유의성을 주장할 표본 크기가 아니다.

CLI가 보고한 캐시 입력은 모든 실행에서 0이었다. 그래도 서버 내부 캐시를 초기화하거나 통제한 것은 아니다. 계정 한도의 과금 가중치도 측정하지 않았다. 원문은 크게 줄었지만 전체 입력 감소가 작았다는 점은 **공통 컨텍스트 비용도 별도로 살펴볼 필요가 있다는 다음 가설**을 준다. 어떤 지침·도구가 몇 토큰을 차지하는지는 이번 실험으로 분해하지 않았다.

벤치마크 자체는 Astra 입력 **112,756**, 출력 **427**, Jev 입력 **1,876**, 출력 **218**토큰을 사용했다. 실험 설계·분석·글 작성에 사용한 부모 및 검토 에이전트 토큰은 이 숫자에 포함되지 않았고 별도 계측하지 못했다. 앞선 방법 검수의 Jev 11회, 입력 5,959·출력 562도 운영 한 번의 비용과 분리한다. 이 작업 전체가 이미 순절감을 만들었다고 주장하지 않는다.
