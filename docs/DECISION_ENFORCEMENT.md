# Tool decisions before execution

`decision_enforcement` requires a Jev effect classification before every hook-visible PreToolUse call that passes the local shell policy. It includes file edits, subagent tools, MCP tools, and covered shell calls. It replaces the older pre-tool risk call rather than adding a second call. Deterministic safety restrictions remain code-owned and may deny a call without asking a model to reconsider them.

The classifier uses the existing [TypeSafe choice API](https://docs.typesafe.ai/api), with `read-only`, `reversible`, `destructive`, `external-side-effect`, and `unknown` as the closed set. This classifies a proposed action's effects; it does not establish user authorization, choose the user's overall plan, replace code generation, or intercept the model's private reasoning.

## Policy

- A valid Jev response is recorded before normal host policy continues. The hook never grants permission or bypasses an approval.
- Low confidence and the unknown class stay UNKNOWN. Native policy remains responsible for the action; the parent LLM is not asked to invent a replacement verdict.
- Missing, invalid, or failed Jev responses deny ordinary actions. Read-only recovery commands and explicitly registered Jev executables can continue under their existing policies so an outage does not prevent diagnosis or required verification.
- Existing verification enforcement remains stronger: direct tests and unknown shell scripts are still denied. Jev cannot override that local rule.
- Matching requests share a 120-second cache, including uncertainty and failure. Cache keys include session, turn, tool, working directory, and argument fingerprint. Cached classification is never proof that a tool already executed or that its inputs remain valid for an action.
- PermissionRequest does not run another classifier or promote the classification to automatic approval. PostToolUse retains the separate execution record.

## Registration

Enable `decision_enforcement` through the existing feature controls after registering and trusting `jev-codex-hooks` with the host. Keep `verification_enforcement`, `verification_gate`, and `verification_assessment` enabled for the verification workflow.

Use `decision_executables` in the feature configuration to register absolute paths to the installed `jev-judge`, `jev-session-read`, `jev-aside`, `jev-macos`, `jev-ios`, `jev-collect`, and `jev-visual` adapters. Their source-checkout bin paths are also recognized. Do not register generic shells, interpreters, or arbitrary executables. Each adapter retains its own argument checks, confidence thresholds, authorization requirements, and action guards. Their shell invocation must be literal and cannot append an unrelated command.

No hook definition or trust hash is generated by this feature. Updating handler source behind an existing registration must still be observed on the running host before claiming live coverage. Disable with `jev-features disable decision_enforcement` from a user-controlled terminal, or through an already authorized recovery workflow.

## Data and limits

Outbound state is limited to 4,000 bytes of tool and argument summaries. Patch bodies, large code bodies, images, credentials, and log bodies are withheld or masked. The cache and audit contain identifiers, fingerprints, decision metadata, and provenance rather than original arguments. Masking is best effort; avoid passing secrets as ordinary text arguments. An oversized or unsupported request may be denied rather than forwarded whole.

The audit separates completed Jev judgments, cached results, UNKNOWN, failures, and recovery continuation. It is not fed back into model context on every successful call. Confidence is a model signal, not a guarantee of correctness; [TypeSafe's confidence guidance](https://docs.typesafe.ai/confidence) describes this boundary.

Hosted tools, hook-exempt paths, input to an already running process, and the internal steps of another agent runtime remain outside the native hook. An observed MCP invocation covers that invocation, not every internal browser operation it may perform. Routing repeated UI actions through the registered Jev adapters extends coverage where those adapters support the action. This is a workflow guard, not an operating-system sandbox or a replacement for system safety policy. Token savings are not yet established.

## Observed validation

The combined focused suite passed 49 tests. After adding tool name and disposition to the audit record, the affected 15 tests passed again; the rest were not repeated. Tests cover metadata privacy, duplicate requests, API failure, recovery, native denial, and the absence of automatic permission grants.

On the active Codex Desktop task, the audit recorded completed live Jev classifications for `Bash`, `apply_patch`, and `mcp__codex_app__list_artifacts`. The edit was classified reversible at confidence 0.9. The MCP call remained UNKNOWN at confidence 0.88, and the shell classification was unknown at confidence 1; both stayed under native policy rather than being relabeled as safe. The separate evidence assessment remained INSUFFICIENT. No extra run was used to seek a more favorable model label.
