# Codex 입력 절감 조사 결과 — 2026-09-22

두 실험을 구분한다. Jev 배치의 Codex 사용량 비교와 스킬 목록의 로컬 렌더링 크기 비교는 서로 다른 측정이며, 절감률을 합산할 수 없다. 이 자료는 보편적인 비용 절감률이나 정확도 동등성을 입증하지 않는다.

## 1. 원문을 코드와 Jev 배치로 처리

동일한 합성 24건을 Codex `gpt-6-astra` / `ultra`로 조건별 한 번 실행했다. 양쪽 모두 사용자 config·MCP·hooks를 제외한 통제된 CLI 실행이며, 모든 스킬/환경의 on/off 비교가 아니다. 입력 데이터는 같지만 워크플로의 도구 호출 횟수는 다르다.

| 측정 | Codex 직접 분류 | Jev 배치 |
| --- | ---: | ---: |
| Codex 입력 토큰 | 81,426 | 58,221 |
| 캐시 제외 입력 토큰 | 22,034 | 19,949 |
| Codex 출력 토큰 | 927 | 166 |
| 정답 / 항목 수 | 24 / 24 | 23 / 24 |
| UNKNOWN | 8 | 9 |

이 한 쌍에서 입력은 28.5%, 캐시 제외 입력은 9.5%, Codex 출력은 82.1% 감소했다. Jev는 별도로 입력 11,863 / 출력 1,444토큰을 사용했다. `text_tokens=681`은 배치 항목 텍스트의 추정량으로 Codex 유입량이 아니다.

차이가 난 `h02`의 Jev 최상위 답은 정답이었지만 confidence 0.87이 사전 고정 기준 0.9에 못 미쳐 UNKNOWN으로 보존했다. 기준을 결과에 맞춰 낮추지 않았다. 캐시는 통제되지 않았으며, 정확도 동등성·전체 비용 절감 주장은 하지 않는다.

## 2. 필요한 스킬을 유지하며 고정 입력 축소

사용자 설정에 `skills.max_context_tokens=3500`, `tool_output_token_limit=1000`을 적용했다. 새 `codex debug prompt-input` 렌더링에서 스킬 127개와 경로를 유지하면서 스킬 영역은 22,262→14,497바이트, 전체 입력 텍스트는 30,854→23,106바이트로 줄었다. 전체 렌더링 크기 감소는 25.1%다. 2,000토큰 예산은 일부 항목을 누락시켜 채택하지 않았다.

이는 과금 토큰 실측이 아니다. 스킬 설명이 짧아졌으므로 실제 선택 정확도와 작업 성공률을 별도로 확인해야 한다. 이미 대화에 들어온 기록을 제거하지도 않는다. [설정과 복구 방법](INPUT_POLICY.md) · [집계 JSON](../benchmarks/jev-offload/input-budget.json)

## 3. 적용한 운영 규칙

- 원문은 코드로 읽고 필요한 경우에만 Jev로 선별한다. Codex에는 ID·경로·줄 범위·짧은 근거를 전달한다.
- 조회는 기본 1,000바이트, 필요한 경우 최대 4,000바이트로 넓힌다. 오류·원본 로그·실제 종료코드는 보존한다.
- 자식 에이전트는 기본 `fork_turns="none"`으로 시작하고 목표·경로·완료 조건·필수 제약만 전달한다.
- UNKNOWN은 유지한다. 환경 오류와 confidence 미달은 코드로 설명하고, 명시적 UNKNOWN의 의미 원인만 Jev에 최대 한 번 물어 추정으로 표시한다.
- 기존 안전 경계와 필요한 검증을 유지한다. 원인 진단을 실행 권한이나 통과 판정으로 바꾸지 않는다.

[UNKNOWN 구현과 실제 호출 경계](UNKNOWN_DIAGNOSTICS.md). 해당 구현의 `npm test`는 267/267을 통과했다. 설정·문서 변경 후에는 새 입력 렌더링과 파일 형식을 확인했으며, 전체 모델 성능 벤치마크를 다시 실행하지 않았다. 개인 설정·키·실제 대화 로그는 저장소에 포함하지 않는다.
