# Workflow routing microbenchmark: frozen before execution

Question: how much Astra input/output does replacing six raw routing records with code/Jev advice avoid at the next model turn, and does the routing answer remain correct?

This is a synthetic routing/reporting stage, not an end-to-end coding task. The treated model receives precomputed answers; the control computes answers from metadata. This information substitution is the intervention, not evidence that Jev makes Astra smarter. Do not generalize a percentage to all coding work, subscriptions or task accuracy. A production caller that only needs structured advice can omit this reporting model turn entirely; this experiment retains it in every condition to measure remaining model ingress.

- Freeze cases, expected answers, prompt, runner and preprocessing code hashes before any measured provider call. Keep the private manifest, raw events, process exit codes and final outputs. Do not change cases or expected answers after seeing results.
- A: Astra receives six minimal raw task metadata records. B: code-only policy with advisor disabled, then Astra receives compact id/strategy records. C: deployed code plus Jev for the two mixed cases, then Astra receives compact id/strategy records. Known cases use no Jev. Conditions B/C use the same compact shape.
- Order is A1, B1, C1, C2, B2, A2. Two observations per condition, same six cases each. These are repeated observations of six cases, not 36 independent tasks.
- Use the same installed Codex CLI, `gpt-6-astra`, effort `ultra`, read-only sandbox, fresh ephemeral session, common prompt and final JSON contract. Ignore the mutable user config and set project documentation budget to zero in every condition; native safety remains. Do not read personal source/history. This isolation is not the fully loaded desktop environment.
- Record effective model when available. Do not silently substitute another model. Each CLI execution has 120 seconds; failure/timeout/noncompliant output is retained without replacement or retry. Stop remaining model executions only on authentication/rate-limit failures and report the missing runs.
- Code/Jev preprocessing runs once per C repetition with fresh plan paths. Repeat plan access separately to measure warm reuse; do not mix warm reuse into cold latency or input totals. Jev uses the deployed 1,500 ms timeout, confidence 0.7, no retries or recursive diagnosis.
- Preserve UNKNOWN. Report exact correct / wrong / UNKNOWN / malformed / incomplete counts separately. A code-only UNKNOWN on mixed cases is expected; it must not be called a success or silently omitted.
- Record prompt UTF-8 bytes, actual CLI-reported input, cached input, uncached input (input minus cached), output and reasoning output when exposed. Missing metrics are null, not zero. Report every run plus means and ranges; output may include reasoning, so do not double count it. Also record Astra time and cold preprocessing time separately.
- Record Jev request attempts, provider-reported tokens and model separately. Sum provider token counts only as an unweighted bookkeeping total, not a cost or Codex quota equivalence. Account billing weights are unknown. Method-review and experiment-design costs are excluded from per-run totals and disclosed as exclusions.
- Server-side cache state cannot be reset or standardized. Reverse order reduces but does not eliminate order/cache effects. Do not call any run a cold Astra cache. Two repetitions cannot establish a stable effect, statistical significance or accuracy parity.
- The run manifest is a local timestamp/hash record, not third-party preregistration. Raw logs stay private; publish sanitized per-run metrics, failures, hashes, fixtures and scripts. Do not publish credentials, personal paths or unrelated session content.
